## 변경 내용

### 신규: `shared/pricing.ts` (단일 소스)

server/ 와 client/ 가 별도 npm 패키지라 공유 수단이 없었다. **npm workspaces 대신
루트 `shared/` 직접 import** 를 택했다 — 개인 프로젝트 규모에서 빌드 단계를 추가하지
않기 위해서다.

- server: `import '../../shared/pricing.js'` (tsconfig `rootDir: ".."`, include에 `../shared` 추가)
- client: `import '@shared/pricing'` (vite alias + tsconfig paths + `server.fs.allow: ['..']`)

> `rootDir` 변경으로 tsc 산출물이 `dist/server/src/` 로 내려가, server의
> `start` 스크립트를 `node dist/server/src/index.js` 로 함께 수정했다.
> dev는 tsx라 영향 없음.

캐시 단가는 Anthropic 표준 비율(write = input × 1.25, read = input × 0.1)로 도출한다.
미지 모델은 Sonnet 단가로 폴백하되 `unknownModels` 로 API 응답에 노출한다.

### 서버

| 파일 | 변경 |

### 평가 지표 — 왜 '효율'이 아니라 '낭비'인가

토큰 총량은 비용(분자)일 뿐이라 평가가 못 된다. 정답 세트 없이 로그만으로 성과(분모)를
추론해야 하는데, **효율(토큰·턴 최소화)을 목표로 두면 thinking을 줄이는 게 이기는 전략**이
되어 Goodhart 법칙에 그대로 걸린다. 그래서 재는 대상을 재작업·실패로 정했다.

`client/src/lib/sessionQuality.ts` (순수 함수, 테스트 10종):

| 지표 | 계산 | 성격 |
|------|------|------|
| 캐시 적중률 | cacheRead / 전체 입력 | 유일하게 트레이드오프 없는 지표 |
| tool 실패율 | tool_result의 `is_error` 비율 | 헛발질 |
| 재작업 파일 | Edit/Write/MultiEdit가 2회 이상 닿은 file_path | 한 번에 못 맞힘 |
| 반복 명령 | 정규화된 동일 Bash 명령 2회 이상 | 탐색 루프 |
| thinking 비중 | thinking 턴 / assistant 턴 | 좋고 나쁨 아님 — **성향** |

### ⚠️ 측정 함정 — 직접 겪은 사례

초기 탐색 스크립트에서 Bash 명령을 `cmd[:40]` 으로 잘라 집계해
`cd .../rag-mfe/ 42회` 라는 결과를 얻고 "명백한 낭비 신호"로 판단했다. **틀렸다.**

전체 명령으로 비교하니 42개는 앞 경로만 같고 뒤가 전부 다른 **서로 다른 명령**이었고,
정확히 동일한 명령의 반복은 **0건**이었다. 절단 길이가 만든 허상이다.

→ `sessionQuality.ts` 는 공백만 정규화하고 **전체 문자열을 비교**한다.
   과소 검출(놓치는 케이스)은 감수하되 **거짓 양성은 만들지 않는 쪽**을 택했다.
   프록시 지표는 거짓 양성이 나오는 순간 신뢰를 잃기 때문이다.

## 3차 작업 — 🔴 requestId 중복 계상 버그 (원본 코드부터 존재)

UI의 "48회 호출"이 무슨 의미냐는 질문에서 드러났다. 확인해보니 **48은 API 호출 수가
아니라 JSONL 라인 수**였고, 실제 요청은 16건이었다.

### 원인

Claude Code는 한 API 응답을 content block(thinking / tool_use / text) 단위로 **여러
JSONL 라인에 나눠 기록**하면서, **같은 `usage` 를 매 라인에 반복**해 넣는다.

```
requestId req_011CdComsvBhp6gZakY4   라인 5개
   content=['thinking']   in=2 out=4   cacheRead=66036
   content=['tool_use']   in=2 out=4   cacheRead=66036
   content=['tool_use']   in=2 out=4   cacheRead=66036
   content=['tool_use']   in=2 out=4   cacheRead=66036
   content=['tool_use']   in=2 out=444 cacheRead=66036   ← 최종
```

`cache_read_input_tokens` 66036이 5번 반복된다. 라인을 그대로 합산하던 기존 코드는
이걸 330,180으로 계산했다. `output_tokens` 는 라인마다 누적 스냅샷이라 **최댓값이
그 요청의 최종값**이다.

실측 부풀림 배율: 요청당 1.75~3.00 라인 → 비용 **1.74~2.57배 과대 계상**.

### 수정

`shared/pricing.ts` 에 `dedupeByRequest()` / `collectUsage()` 추가. requestId 기준으로
묶고 `output_tokens` 최대인 라인 1건만 남긴다. requestId 없는 라인은 개별 요청 취급.

적용: 서버 `/cost`, `TokenDashboard.calcStats`, `GlobalAnalytics`, `App.tsx` 4곳 전부.
회귀 테스트 5종 추가(실측 사례 48895×3 그대로 픽스처화).

라벨도 `N회 호출` → `API 요청 N회` 로 정정. 기존 라벨은 라인 수를 호출 수로 오도했다.

### 비용 이력 정정 (세션 f966e952)

| 시점 | 값 | |
|------|-----|---|
| 원본 코드 (메인만·Sonnet 고정·라인합산) | $40.92 | |
| 1차 수정 후 (서브+모델별, **라인합산 버그 잔존**) | $109.56 | ❌ 허수 |
| 2차 수정 후 (requestId 중복 제거) | **$42.97** | ✅ |

**1차 작업에서 보고한 "2.68배 개선"은 틀렸다.** 서브에이전트를 포함시킨 건 맞지만
중복 계상 버그가 그대로 있어 양쪽 다 부풀려진 값이었다. 실제 개선폭은 1.05배다.

### 교훈

두 번 연속 **측정 방식 자체의 결함**에 속았다 (40자 절단 → 허위 반복 명령,
라인 합산 → 허위 비용). 집계 결과가 "그럴듯한 크기"로 나오면 검증을 멈추게 되는데,
**분모/단위가 무엇인지(라인? 요청? 턴?)를 먼저 확정**하지 않으면 그럴듯한 오답이 나온다.
`requestId` 같은 그룹핑 키가 데이터에 있는지 먼저 확인할 것.
